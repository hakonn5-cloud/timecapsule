# ADR-0001. Выбор метода развёртывания приложения TimeCapsule на Amazon EC2

- **Статус:** принято
- **Дата:** 2026-10-06
- **Специальность:** Informatică aplicată
- **Автор:** Zui Artiom

---

## 1. Контекст

Для функционирования сервиса TimeCapsule развёрнут единый виртуальный сервер Amazon EC2 (`t3.micro`, Amazon Linux 2023) в регионе `eu-central-1` (Frankfurt). На сервере функционирует веб-стек, состоящий из:
- Nginx (веб-сервер / reverse proxy);
- PHP-FPM 8.4 (обработчик скриптов приложения через unix-сокет);
- PostgreSQL 16 (локальная реляционная база данных);
- Локальная файловая система EBS (`storage/uploads` и сессии).

Исходный код приложения поддерживается в публичном репозитории GitHub организации `hakonn5-cloud/timecapsule`.

Перед нами стояла задача выбора способа доставки обновлений (deployment) кода из репозитория на работающий продакшен-сервер EC2. Способ должен обеспечивать воспроизводимость, минимизацию времени простоя (downtime), сохранность пользовательских данных (база данных и загруженные файлы) и соответствовать учебному треку специальности *Informatică aplicată*.

---

## 2. Решение

Выбран **Вариант A: ручной выпуск новой версии через Git на сервере**.

Последовательность шагов развёртывания:
```bash
cd /var/www/timecapsule
git pull
composer install --no-dev --optimize-autoloader
php bin/init-db.php
sudo systemctl reload php-fpm
```

Данная последовательность выполняется инженером вручную через интерактивную SSH-сессию на инстансе EC2.

---

## 3. Рассмотренные альтернативы

### Альтернатива 1: Прямое копирование файлов по SSH/SCP (`scp -r`)
- **Описание:** Разработчик локально собирает или модифицирует файлы проекта и копирует их на сервер поверх существующей директории с помощью `scp` (как это делалось в Части 1 лабораторной для статического сайта).
- **Почему отвергнуто:** 
  - Нарушает базовый принцип современной разработки: *«Единственный источник истины — система контроля версий (Git)»*.
  - Код попадает на сервер в неконтролируемом состоянии (untracked changes, возможно случайное копирование временных файлов или ключей).
  - Крайне высокий риск рассинхронизации: легко забыть скопировать отдельный файл или скопировать файл с правами, недоступными для пользователя веб-сервера (`apache`).
  - Невозможно провести быстрый и детерминированный откат (rollback): при сбое придется вручную искать и заменять поврежденные файлы.
  - На сервере отсутствует история изменений.

### Альтернатива 2: Автоматизированный скрипт `deploy.sh` на сервере (Вариант B)
- **Описание:** Все шаги деплоя упаковываются в bash-скрипт `~/deploy.sh` с флагами `set -euo pipefail` и `git pull --ff-only`, запускаемый локально или удаленно по SSH (`ssh ec2-user@<IP> ./deploy.sh`).
- **Сравнение:** Скрипт уменьшает вероятность человеческой ошибки (пропуск команды или опечатка) и стандартизирует процедуру. Однако в рамках требований программы для специальности *Informatică aplicată* предписан Вариант A (пошаговое ручное выполнение) для детального освоения каждого этапа жизненного цикла развертывания (получение diff, установка зависимостей, миграция схемы БД, grace-перезагрузка worker-процессов PHP-FPM).

### Альтернатива 3: Автоматический CI/CD пайплайн (GitHub Actions / AWS CodeDeploy)
- **Описание:** Автоматический триггер деплоя при пуше в ветку `main` без ручного входа по SSH на сервер.
- **Сравнение:** Промышленный стандарт, исключающий доступ разработчиков на продакшен-машины. Отложен до последующих лабораторных работ курса, так как требует настройки безопасного взаимодействия между GitHub и AWS через OpenID Connect (OIDC) или IAM Roles, а также механизмов оркестрации.

## 4. Сравнительная таблица методов

| Критерий | Копирование по SCP | Ручной `git pull` (Вариант A) | Скрипт `deploy.sh` (Вариант B) |
| :--- | :--- | :--- | :--- |
| **Источник правды** | Ноутбук разработчика | GitHub репозиторий | GitHub репозиторий |
| **Воспроизводимость** | Низкая (человеческий фактор) | Высокая | Очень высокая |
| **Контроль версий на сервере** | Отсутствует | Полный (`git log`) | Полный (`git log`) |
| **Простота отката (Rollback)** | Сложно / Вручную | Быстро (`git revert` + `git pull`) | Быстро (`git revert` + `run deploy.sh`) |
| **Риск ошибки оператора** | Критический | Средний (требует внимания) | Минимальный |
| **Атомарность обновления** | Нет | Нет (файлы обновляются поочередно) | Нет |
| **Подходит для учебных целей** | Только для статики | **Идеально (понимаем каждый шаг)** | Удобно для рутины |

## 5. Последствия принятого решения

### Положительные последствия (+)
1. **Прозрачность:** Инженер видит вывод каждой команды (`git pull` показывает измененные файлы, `composer install` сообщает о добавленных пакетах, `init-db.php` рапортует о статусе схемы БД).
2. **Контроль и диагностика:** Если какой-либо шаг падает (например, конфликт миграции БД или ошибка зависимостей), выполнение немедленно прерывается под контролем инженера, позволяя изучить логи без риска сломать сервис дальше.
3. **Безопасность репозитория:** Сервер работает по HTTPS-ссылке на публичный репозиторий в режиме «только чтение». Серверу не требуются SSH-ключи с правом записи на GitHub, что защищает исходный код даже при компрометации виртуальной машины.
4. **Легкость отката:** Процедура отката полностью детерминирована: создается коммит отмены (`git revert HEAD`), отправляется в репозиторий и подтягивается на сервер (`git pull`), возвращая рабочее состояние приложения за несколько секунд.

### Недостатки и риски (-)
1. **Отсутствие атомарности (Zero-Downtime Deployment):** В момент выполнения `git pull` файлы обновляются на диске последовательно. Пользователь, отправивший запрос в этот 2-3 секундный интервал, может получить неконсистентное состояние (часть файлов старых, часть новых).
2. **Человеческий фактор:** Риск забыть перезагрузить PHP-FPM (`sudo systemctl reload php-fpm`), из-за чего опкод-кэш OPcache продолжит выполнять старый байт-код из памяти.
3. **Необходимость прямого SSH-доступа:** Разработчик должен иметь сетевой доступ по порту 22 к продакшен-серверу.

---

## 6. Меры по минимизации рисков
- Все конфигурационные параметры и пароли отделены от кода и хранятся в `.env` (права `640`, группа `apache`).
- Перед выпуском правок на продакшен код верифицируется локально.
- В последующих лабораторных работах планируется переход к непрерывной интеграции (CI/CD) и Blue-Green/Rolling деплою с балансировщиком нагрузки Application Load Balancer.
