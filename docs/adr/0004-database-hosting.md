# ADR-0004. Размещение базы TimeCapsule в Amazon RDS

- **Статус:** принято; заменяет выбор EC2 для БД в [ADR-0002](0002-database-placement.md)
- **Дата:** 2026-11-04
- **Специальность:** Informatică aplicată
- **Автор:** Zui Artiom

## 1. Контекст

В ЛР3 PostgreSQL 16 размещался на отдельном EC2 `timecapsule-dev-db` в приватной подсети. Обновления ОС и СУБД, резервное копирование и восстановление требовали ручного обслуживания; для установки пакетов использовался временный NAT Gateway. Вложения уже перенесены в S3 по [ADR-0003](0003-attachment-storage.md).

Для учебного приложения нужны приватное подключение, управляемые резервные копии, небольшой бюджет и возможность остановки между занятиями. Круглосуточная доступность при отказе зоны пока не требуется. Миграция должна сохранить данные и имя, используемое приложением.

## 2. Решение

Использовать `timecapsule-dev-rds`: RDS for PostgreSQL 16.15, `db.t4g.micro`, Single-AZ в `eu-central-1a`, 20 GiB gp3 без autoscaling. Группа `timecapsule-dev-db-subnets` включает приватные подсети в `eu-central-1a` и `eu-central-1b`; наличие двух подсетей само по себе не создаёт standby. Publicly accessible — No; `timecapsule-dev-rds-sg` принимает TCP 5432 только от `timecapsule-dev-web-sg`. Шифрование хранилища и deletion protection включены.

База и пользователь приложения — `timecapsule`; `dbadmin` используется только для администрирования. Настройки подключения остаются вне Git. PHP PDO получает `DB_SSLMODE=require` через DSN: трафик шифруется, но этот режим не равнозначен `verify-full` с проверкой имени сервера. Для усиления проверки нужны доверенный CA и имя, соответствующее сертификату RDS.

Приватная запись `db.timecapsule.internal` — CNAME с TTL 60 на `timecapsule-dev-rds.cr4myc6kwzsa.eu-central-1.rds.amazonaws.com`. Приложение сохраняет `DB_HOST=db.timecapsule.internal`; IP RDS не закрепляется в конфигурации. После проверки переноса и записи новой капсулы исходный EC2 db-server удалён.

Каждый день в 23:00 `Europe/Chisinau` расписание `timecapsule-dev-rds-nightly-stop` вызывает `StopDBInstance`. Execution role `timecapsule-dev-scheduler-role` имеет только необходимое право остановки этой базы. Перед занятием базу запускаем вручную; автоматического утреннего запуска нет.

## 3. Рассмотренные альтернативы

| Вариант | Обслуживание и восстановление | Отказ зоны | Стоимость и выбор |
| --- | --- | --- | --- |
| PostgreSQL на EC2 | Полный контроль над ОС; обновления, dumps, WAL-архив и проверки восстановления настраиваем сами | Один сервер без отдельно созданной репликации не обеспечивает переключение | EC2 + EBS + резервные копии и обслуживание. Отклонён из-за ручных операций |
| **RDS Single-AZ** | AWS обслуживает платформу; автоматические backups и PITR | Standby нет; возможен длительный простой и восстановление в другой зоне | Один DB instance и хранилище; можно останавливать. **Выбран для учебной нагрузки** |
| RDS Multi-AZ DB instance с одним standby | Синхронный standby в другой зоне; резервные копии и обслуживание управляются AWS. Standby не обслуживает SELECT | Автоматическое переключение, endpoint сохраняется; клиентам нужно переподключиться | Оплачиваются primary и standby с соответствующим storage. Выбрать для требований высокой доступности; в лабораторной не развёрнут |
| Aurora PostgreSQL-Compatible | Управляемый кластер, распределённое хранилище в трёх AZ, readers и отдельные endpoints | Для быстрого переключения вычислений нужен Aurora Replica в другой зоне; одного writer недостаточно для готового standby | Provisioned instances либо Serverless v2, storage и модель оплаты I/O. Для текущей нагрузки сложнее и избыточно; не развёрнута |

Сравнение Multi-AZ относится к DB instance deployment с одним standby, а не к Multi-AZ DB cluster с двумя читаемыми экземплярами. Все варианты требуют резервного копирования: репликация также переносит ошибочный DELETE.

## 4. Последствия

### Резервные копии, RPO и восстановление

У включённой RDS автоматический backup выполняется ежедневно в окне 00:56–01:26 UTC, срок хранения — 7 дней. Журналы транзакций выгружаются примерно каждые пять минут. При аварии потенциальная потеря определяется разницей между временем сбоя и фактическим `LatestRestorableTime`: ориентир — несколько последних минут, а не гарантированная верхняя граница в пять минут. Для восстановления после ошибочного DELETE сознательно выбирается более ранний момент; полезные записи после него тоже могут потребовать отдельного переноса.

PITR создаёт новый экземпляр; затем проверяются данные, SG и соединение, CNAME переключается на новый endpoint. RTO включает создание и запуск, восстановление, проверку и обновление DNS; по этому стенду гарантированный срок не измерялся. Остановленная база не принимает записи и не создаёт новые автоматические backups; срок хранения не расходуется за время остановки. Поэтому ночное расписание перекрывает текущее окно backups: нельзя обещать ежедневный свежий snapshot при работе только днём. Для регулярной эксплуатации окно нужно перенести на время доступности базы и проверять `LatestRestorableTime`.

При переносе сохранён локальный CUSTOM dump и сверены данные источника и RDS. Это копия на момент миграции, а не актуальная копия последующих изменений. Перед окончательным удалением RDS необходим свежий dump и сохранение нужных вложений S3.

### Расходы и остановка

Учебная оценка из условия ЛР5 (Frankfurt, ставки за октябрь 2026): `0,019 USD/час` для экземпляра и примерно `2,60 USD/месяц` за 20 GiB. При 3 часах в день и 30 днях получаем `90 × 0,019 + 2,60 ≈ 4,31 USD/месяц`; за 90 дней — около `12,93 USD`. При 730 часах работы — около `16,47 USD/месяц`. Это оценка по методичке, а не проверенный текущий тариф или сумма Bills; налоги, EC2, публичные IPv4, Route 53, S3, дополнительные backups и возможные CPU credits в расчёт не включены.

Официальная страница цен проверена 04.11.2026; точные региональные ставки для выбранного класса в доступном текстовом представлении не показаны. Перед рабочим развёртыванием их следует пересчитать в AWS Pricing Calculator. Для Multi-AZ бюджет определяется тарифами двух экземпляров и соответствующего storage; грубый ориентир — удвоение базовой стоимости БД, но это не точная котировка. Aurora нужно считать отдельно по выбранным вычислениям, storage и I/O; применять к ней цену `db.t4g.micro` нельзя.

Во время Stop прекращается оплата вычислений RDS, но продолжается оплата provisioned storage и применимого backup storage. Через семь суток AWS запускает базу автоматически; ежедневное расписание ограничивает работу до следующего успешного вечернего вызова, но не обеспечивает мгновенную остановку или жёсткий денежный лимит. При вызове для уже остановленной базы API возвращает `InvalidDBInstanceState`; это ожидаемая ошибка состояния. Budget уведомляет о расходах, а не запрещает их.

По условию курса ресурсы Части 2 сохраняются для следующих работ. Отдельно принято намерение после сохранения результатов удалить платную инфраструктуру: эта очистка не выполнена данным ADR или коммитом и завершит доступность стенда. Простая остановка не обеспечивает нулевые расходы.

### DNS и отказ eu-central-1a

После обычного Stop/Start endpoint сохраняется, IP может измениться; в задании 11 сохранились и endpoint, и IP `10.28.10.172`. CNAME позволяет приложению использовать одно логическое имя и при восстановлении на новом экземпляре. 04.11.2026 обнаружена A-запись на адрес удалённого EC2; её замена на CNAME восстановила `/health` с 500 до 200. Этот DNS-сбой рассматривается отдельно от краткого простоя при Reboot.

При потере `eu-central-1a` текущая Single-AZ база не переключится автоматически на `private-b`: там нет standby. При доступных backups потребуется восстановить экземпляр в `eu-central-1b`, проверить соединение и сменить CNAME на новый endpoint. В этой же зоне отказа находится app-server, поэтому одной замены БД недостаточно: приложение тоже нужно развернуть в доступной зоне, восстановить конфигурацию, доступ к S3 и при необходимости bastion, переключить входной трафик. PHP-сессии сейчас локальные; пользовательские сессии могут потеряться.

Для меньшего простоя нужны Multi-AZ БД и приложение как минимум в двух зонах с балансировщиком и подходящим хранением сессий. Multi-AZ сохраняет имя endpoint при failover, но не устраняет переподключение, DNS-кэш и сбои других компонентов. Бюджет такого решения включает резервную БД, дополнительный app-server, балансировщик и связанные сетевые ресурсы.
