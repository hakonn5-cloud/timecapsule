# ADR-0003. Хранение вложений пользователей в Amazon S3

- **Статус:** принято
- **Дата:** 2026-10-22
- **Специальность:** Informatică aplicată
- **Автор:** Zui Artiom

## 1. Контекст

TimeCapsule хранит записи капсул в PostgreSQL на отдельном db-server. До ЛР4 вложения лежали в `/var/www/timecapsule/storage/uploads` на EBS app-server. Такая связь с диском затрудняет замену сервера и распределение запросов между несколькими экземплярами: другой сервер не получает автоматически те же файлы.

Файлы загружаются целиком и читаются по имени. Приложению не нужны изменение отдельных байтов, блокировки или общая POSIX-файловая система. Требуются закрытый доступ до открытия капсулы, сохранение исходного имени при скачивании, защита истории и возможность заменить app-server без переноса вложений.

## 2. Решение

Хранить вложения в закрытом бакете `timecapsule-dev-uploads-hakonn5` региона `eu-central-1` под префиксом `uploads/`. В базе оставлять случайное имя без префикса: это сохраняет совместимость старых записей после миграции.

Использовать AWS SDK for PHP v3 в `src/storage.php`. Загрузка выполняется через `PutObject` с MIME-типом, удаление — через `DeleteObject` без VersionId. После проверки видимости капсулы и времени открытия приложение возвращает HTTP 302 на подписанный `GetObject` сроком 300 секунд. Браузер получает байты непосредственно из S3; параметры ResponseContentType и ResponseContentDisposition задают показ inline или скачивание под исходным именем, включая UTF-8.

Роль `timecapsule-dev-app-role` прикреплена к app-server через instance profile, доверяет сервису EC2 и получает временные учётные данные через IMDS. Политика `timecapsule-dev-app-s3` версии 2 разрешает только `GetObject`, `PutObject`, `DeleteObject` для объектов `uploads/*`. Разрешение `ListBucket`, нужное для CLI-миграции, удалено; прав на уничтожение версий и изменение настроек бакета нет. Постоянные ключи в код и `.env` не добавляются.

В бакете включены Block Public Access, ACL disabled, SSE-S3, Versioning и явный запрет запросов без HTTPS. Правило `timecapsule-dev-noncurrent` действует на `uploads/`: переход неактуальных версий в Standard-IA через 30 дней, удаление через 90 дней с сохранением двух самых новых неактуальных версий, прекращение незавершённых multipart uploads через 7 дней.

## 3. Рассмотренные альтернативы

| Критерий | EBS app-server | Amazon EFS | Amazon S3 — выбран |
| --- | --- | --- | --- |
| Модель доступа | Блочное устройство и локальная файловая система | Общая файловая система, NFS | Объекты по HTTPS API |
| Замена app-server | Нужен сохранённый том, перенос данных или восстановление | Новый сервер подключает ту же файловую систему | Новый сервер использует тот же бакет и роль |
| Несколько app-server | Обычный корневой том не даёт общего каталога; Multi-Attach требует отдельного проектирования | Общий каталог для нескольких клиентов | Все экземпляры используют одни и те же ключи |
| Выдача файла браузеру | Сервер читает и передаёт байты | Сервер читает и передаёт байты | Подписанный URL, передача напрямую из S3 |
| История и удаление | Собственные резервные копии/снапшоты | Резервное копирование и правила доступа | Versioning, Delete markers, lifecycle, IAM |
| Дополнительная работа | Управление томом и согласованностью копий | Mount targets, SG, NFS, управление монтированием | SDK, роль, политика бакета и lifecycle |
| Соответствие задаче | Просто для одного сервера, но сохраняет зависимость вложений от его диска | Подходит, если нужна файловая семантика; для отдельных вложений она избыточна | Соответствует загрузке целых файлов и прямому скачиванию |

EBS не исчезает автоматически при любом сбое EC2: судьба тома зависит от его сохранности и DeleteOnTermination. Однако хранение вложений на корневом томе связывает их обслуживание и восстановление с конкретным сервером и его зоной доступности. EFS решает общий доступ, но не даёт преимуществ POSIX для текущего интерфейса приложения; выбор S3 обусловлен требованиями, а не универсальным превосходством одного сервиса.

## 4. Последствия

### Доступ и срок ссылки

Права пользователя приложения проверяет PHP-контроллер до создания ссылки. S3 проверяет подпись и права роли. Владелец действующей ссылки может передать её другому человеку: S3 не привязывает её к приложенческой сессии, и она допускает повторное использование до окончания срока.

Срок ограничен 300 секундами и оставшимся сроком временных учётных данных; отзыв разрешений или недоступность объекта могут прекратить доступ раньше. Новое обращение к приложению создаёт новую ссылку. URL с подписью нельзя менять после выдачи и нельзя публиковать целиком, пока он действует. Выдача ссылки не включает публичный доступ к бакету.

### Защита истории и стоимость

Обычное удаление в версионируемом бакете создаёт Delete marker и сохраняет предыдущую версию. Приложение не имеет `DeleteObjectVersion`, поэтому его роль не может непосредственно уничтожить историю. Это не полная резервная копия: администратор с более широкими правами может удалить версии, а запрет доступа или удаление текущего объекта могут нарушить работу.

Lifecycle ограничивает рост старой истории, но не гарантирует удаление каждой версии строго на 90-й день: должны выполняться возрастное условие и условие сохранения двух самых новых неактуальных версий. Малые объекты менее 128 KB по стандартным правилам переходов не переводятся в другой класс без настройки исключений. Действующие объекты, две сохранённые старые версии и Delete markers могут оставаться; переходы, запросы и скачивания также оплачиваются. Очистка истёкших Delete markers в этом правиле не включена.

### Несколько серверов и балансировщик

Каждый app-server может использовать один бакет и одинаково ограниченную роль. Копировать вложения между экземплярами и направлять скачивание через балансировщик не потребуется. После перехода на ALB нужно настроить адрес приложения, доступ от группы балансировщика и исходящий доступ серверов к S3.

При этом сессии PHP остаются файлами в `storage/sessions`. Общий бакет вложений не делает приложение полностью stateless: для нескольких серверов нужно отдельное решение для сессий, предпочтительно общее хранилище; sticky sessions лишь временно снижают проблему и не сохраняют сессию при потере экземпляра. Данные PostgreSQL и резервное копирование БД также остаются отдельной задачей.

### Границы решения

Приложение зависит от доступности S3 и разрешений роли. Запись объекта и создание записи PostgreSQL — две отдельные операции без общей транзакции: при сбоях возможны несвязанные объекты, для которых в дальнейшем потребуется сверка и очистка. Региональная отказоустойчивость не реализована одной настройкой Versioning: для переживания потери региона нужно отдельно спроектировать межрегиональную репликацию объектов, доступ и переключение приложения, а также восстановление БД.

## 5. Проверка решения

В заданиях 10–13 подтверждены перенос старого PNG с сохранением ключа, создание новых JPG/PDF, корректные MIME-типы, исходное имя PDF, чтение старого вложения из S3, ссылка на 300 секунд и отказ после истечения срока. Удаление капсулы сохраняет версию под Delete marker.

После удаления локальной папки и её резервной копии приложение создало новую капсулу с вложением. После исключения ListBucket проверены загрузка, открытие, скачивание и удаление, а запрос списка с app-server отклонён. Для отсутствующего объекта CLI получил 403 от имени роли и 404 от имени пользователя с ListBucket. Доказательства находятся в [отчёте ЛР4](../lab4/README.md).
