# ADR-0002. Размещение базы данных PostgreSQL в изолированной приватной подсети Amazon VPC

- **Статус:** принято
- **Дата:** 2026-10-13
- **Специальность:** Informatică aplicată
- **Автор:** Zui Artiom

---

## 1. Контекст

В лабораторной работе №2 приложение TimeCapsule функционировало в монолитной конфигурации: Nginx, PHP-FPM и СУБД PostgreSQL 16 размещались на одном сервере `webserver` внутри публичной подсети Default VPC. 

Такой подход несёт серьёзные риски информационной безопасности и ограничения архитектуры:
1. База данных делит аппаратные ресурсы (CPU, RAM, дисковый ввод-вывод) с веб-сервером и PHP-обработчиком. При всплеске веб-трафика СУБД может испытать дефицит памяти.
2. При компрометации веб-приложения (например, через уязвимость в коде или инъекцию) злоумышленник получает прямой доступ к локальной файловой системе и сокету СУБД.
3. Отсутствует эшелонированная сетевая защита (Defense in Depth).

В рамках лабораторной работы №3 спроектирована собственная виртуальная сеть Amazon VPC (`timecapsule-dev-vpc`, `10.28.0.0/16`) с двумя зонами доступности (`eu-central-1a`, `eu-central-1b`), публичным контуром (Internet Gateway) и приватными сегментами. Встал вопрос выбора архитектурного размещения базы данных приложения.

---

## 2. Решение

Принято решение: **разместить СУБД PostgreSQL на выделенном инстансе `db-server` в изолированной приватной подсети (`timecapsule-dev-private-a`, `10.28.10.0/24`) без публичного IP-адреса и без постоянного маршрута в интернет.**

Взаимодействие компонентов организовано следующим образом:
1. Веб-сервер (`app-server`) находится в публичной подсети `public-a` (`10.28.0.0/24`) и имеет Elastic IP для доступа пользователей.
2. `db-server` не имеет публичного IP и находится в подсети с таблицей маршрутизации `private-rt`, где нет маршрута `0.0.0.0/0` в Internet Gateway.
3. Сетевой экран `db-sg` разрешает входящие TCP-подключения к порту 5432 строго из группы безопасности `web-sg`, а порт 22 (SSH) — строго из группы `bastion-sg`.
4. Внутреннее разрешение имён обеспечивается приватной зоной AWS Route 53 (`timecapsule.internal`), где A-запись `db.timecapsule.internal` указывает на приватный IP СУБД (`10.28.10.228`).

## 3. Рассмотренные альтернативы

### Альтернатива 1: Размещение базы на одном сервере с приложением (как в ЛР2)
- **Плюсы:** Минимальная стоимость (один инстанс `t3.micro`), отсутствие сетевых задержек при межсерверных запросах (unix domain socket / localhost).
- **Минусы:** Отсутствие масштабируемости, единая точка отказа, нулевая сетевая изоляция. Неприемлемо для production-архитектур.
- **Вердикт:** Отклонено как не отвечающее требованиям безопасности и надежности.

### Альтернатива 2: Отдельный сервер базы данных в публичной подсети
- **Плюсы:** Простота установки обновлений (прямой выход в интернет через Internet Gateway).
- **Минусы:** Сервер базы данных имеет публичный IP-адрес или находится в подсети с прямым маршрутом во внешний мир. Защита опирается исключительно на правила Security Group. В случае ошибки конфигуратора (например, случайного открытия `0.0.0.0/0` на порт 5432) база мгновенно становится мишенью сканеров Shodan и автоматических брутфорс-атак.
- **Вердикт:** Отклонено, так как нарушает принцип Defense in Depth.

### Альтернатива 3: Отдельный сервер в приватной подсети (Выбранный вариант)
- **Плюсы:** Трёхуровневая эшелонированная защита (отсутствие маршрута и внешнего адреса + фильтрация на уровне SG + аутентификация `pg_hba.conf` и SCRAM-SHA-256). База физически недостижима из интернета.
- **Минусы:** Для установки пакетов и обновлений безопасности требуется организация временного NAT-шлюза.

---

## 4. Последствия

### 4.1. Обновление ОС и пакетов на `db-server` без постоянного выхода в интернет
- Поскольку постоянный NAT Gateway в AWS обходится дорого (~$38 в месяц / $1.25 в день), для СУБД принята модель **временного (on-demand) NAT Gateway**.
- При необходимости установки обновлений безопасности администратор разворачивает временный NAT Gateway в `public-a`, добавляет маршрут `0.0.0.0/0` в `private-rt`, выполняет `sudo dnf update` и немедленно удаляет шлюз и освобождает Elastic IP.
- За счёт этого затраты на NAT сводятся к нескольким центам за сессию обслуживания вместо фиксированных ~$38 ежемесячно.

### 4.2. Использование Elastic IP на `app-server` и перспектива интеграции балансировщика (ALB)
- В текущей архитектуре сервер приложения `app-server` снабжён статическим **Elastic IP (`timecapsule-dev-app-eip`)**. Это исключает смену IP-адреса и необходимость перенастройки параметра `APP_URL` при плановых перезапусках инстанса.
- В последующих лабораторных работах перед серверами приложений будет развёрнут **Application Load Balancer (ALB)**:
  - Публичный трафик пользователей будет поступать на DNS-имя балансировщика, распределённого по двум публичным зонам.
  - Сам `app-server` будет перенесён в приватную подсеть (`private-a` / `private-b`) и потеряет Elastic IP.
  - Доступ к приложению по HTTP будет разрешён только от группы безопасности балансировщика (`alb-sg`).
  - Необходимость в индивидуальном Elastic IP для сервера приложений полностью отпадёт, что повысит защищённость и снизит расходы.
